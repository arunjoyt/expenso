# Receipt extraction tracking: correction-based accuracy, dedicated log DocType

**Update:** the log DocType is named `LLM Call Log` (not `Receipt Extraction Log`), with a `feature` field (e.g. `"receipt_extraction"`), since a chat feature (issue #44) is planned and will also make OpenAI calls needing the same latency/token/cost tracking. This was a same-session refinement made before any code existed, so this ADR is updated in place rather than superseded — everything below applies to `LLM Call Log` filtered to `feature = "receipt_extraction"`. Accuracy fields remain specific to what a feature can measure; chat has no obvious equivalent to "did the Member correct this field" and isn't expected to populate them.

Receipt extraction (ADR 0002) needed latency/token/cost/accuracy tracking for the OpenAI calls it makes. The hardest part is "accuracy" — there is no ground-truth oracle for a receipt (no second OCR pass, no manual grading pipeline). We defined accuracy as **field-level agreement between what the LLM extracted and what the Member actually saved**: for each of `amount`/`date`/`category`/`notes`, did the Member's final saved value match the extracted value. This is a correction signal, not a truth signal — it measures "how often did the Member need to fix this," which is the only thing observable without building a separate grading workflow. A reader should not assume "accuracy" here means verified-correct; it means unedited-by-the-Member.

Two refinements to that definition: fields the LLM returned as `null` are excluded from the accuracy calculation entirely (there was no claim to grade — a Member filling in a gap isn't the LLM being "wrong"), and `notes` uses the same exact-string-match rule as the structured fields even though Members often append context to it, accepting that this may under-state notes accuracy in practice. Both can be revisited once real data shows whether they're informative.

Storage is a new DocType, `LLM Call Log`, rather than reusing Frappe's built-in `Integration Request` — this data is meant to be queried and reported on (list view filters, Number Cards, a daily-trend Script Report), and structured fields (`feature`, `latency_ms`, `input_tokens`, `output_tokens`, `cost`, `model`, per-field accuracy) serve that better than unpacking JSON blobs. It's System Manager-only — this deliberately doesn't follow the Family-scoped permission pattern used by Expense/Income/Budget, since Chat's rows also carry full private conversation trace content (ADR 0004) that no Member, including the one who wrote it, should be able to list.

**Update:** Members do get to see their *own* cost, though — not by relaxing `LLM Call Log`'s permissions, but via a narrow, purpose-built API (`get_my_llm_cost`) that aggregates just the calling Member's own rows into a dollar total (current month, with a Receipt/Chat breakdown), shown in Settings. This is a meaningfully different thing from list access: the API can never return another Member's cost or any row's raw `content`/trace, only a number derived from the caller's own data. `LLM Call Log` the DocType stays System Manager-only for everything else (list view, admin reports, trace content) — this is the one deliberate, narrow exception.

Because extraction (`extract_receipt`) and save (`create_expense`) are two separate requests, and accuracy can't be computed until save happens, `extract_receipt` returns the new log row's `name` to the frontend, which passes it back into `create_expense`. That call updates the same row with final values, computed accuracy, and a link to the created Expense. If the Member abandons the flow without saving, the row simply stays unlinked with accuracy fields unset — still valid for latency/token/cost stats. Rate-limited attempts (blocked before ever calling OpenAI) don't create a log row at all, since they have nothing to report on any of these dimensions and would just dilute the aggregates.

Per-token pricing used to compute `cost` is a hardcoded constant in code rather than admin-editable, since it changes rarely and a code change gives a clear, versioned record of when and why it changed.

**No third-party observability platform** (Langfuse, Helicone, LangSmith, etc.) either, despite these being the default reach-for in the LLM-engineering space. Two reasons hold regardless of feature: the accuracy signal is inherently domain-specific (Receipt's Member-correction comparison, tied to `create_expense`'s own save flow) — no external tool tracks that out of the box, so the linking logic (ADR 0003, above) would still have to be hand-written either way, and a third-party tool would only relocate where the numbers land, not remove the work. And for a 2-user personal app, self-hosting one (Langfuse) means running and maintaining a second service alongside the single Frappe bench this app otherwise needs, while a hosted option (Helicone's proxy) means routing receipt photos and chat content — both genuinely sensitive, financial and personal — through a third party. `#68`'s admin reporting (Number Cards + Script Report) was deliberately built to keep cost/accuracy visibility inside the one Frappe Desk surface already used for everything else in this app, rather than fragmenting it into a second dashboard. Chat's tool-calling shape (see ADR 0004) is the closest this app comes to needing a real trace viewer — revisit if reading raw JSON traces in Desk actually proves painful in practice, not preemptively.
