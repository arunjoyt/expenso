# Chat via MCP connector (ChatGPT/Claude) — proposed alternative to ADR 0004, not yet decided

**Status: proposed, undecided.** This ADR records an alternative to ADR 0004's in-app hand-rolled tool-calling design, worked out in a grill-with-docs session (2026-08-06) that asked "could Chat be delivered via a ChatGPT/Claude connector instead of building #69-71?" ADR 0004 remains the current, committed design — issues #69/#70/#71 are unchanged and still the plan of record. This document exists so the alternative's shape and trade-offs are on record if it's picked up later, without prejudging the choice. Motivated in part by shifting the LLM API cost off Expenso's own OpenAI billing and onto the Member's ChatGPT/Claude subscription (the same cost-shift goal [ADR 0006](0006-chat-driven-manual-entry-mcp-connector.md) states explicitly) — see the "no OpenAI/Anthropic call for Expenso to meter" point below.

**Note:** a related but separate write-capable proposal — general chat-driven manual entry (`create_expense`/`create_income`, no photo required) reusing this same MCP server under a distinct write scope — is recorded in [ADR 0006](0006-chat-driven-manual-entry-mcp-connector.md), also proposed but undecided.

**The alternative.** Instead of an in-app floating bubble, full-screen thread, and hand-rolled tool-calling loop inside Expenso, expose the same 4 read-only whitelisted methods (`get_expenses`, `get_analytics`, `get_income`, `get_budgets`) as tools on a remote MCP server, built with the official `mcp` Python SDK (a protocol-correctness call, not an agent-framework one — MCP's wire protocol is versioned and non-trivial to hand-roll correctly, unlike the simple bounded loop ADR 0004 rejected a framework for). Auth reuses Frappe's existing built-in OAuth2 provider (`OAuth Client` doctype, standard Authorization Code flow) — whitelisted methods already run correctly under an OAuth-resolved user via `frappe/auth.py::validate_auth()` → `validate_oauth()` → `frappe.set_user()`, so Family-scoped permissions apply with zero new permission logic. A Member reaches Chat by adding this MCP server as a connector inside ChatGPT or Claude's own app — a "power user" surface, not the bottom-bar/floating-bubble entry point issue #44 originally asked for.

**What this would drop from ADR 0004's design, if chosen:**
- `Chat Message` DocType, `send_message`, `get_chat_history`, `clear_chat()` — gone. ChatGPT/Claude hold conversation history client-side; Expenso never stores or sees a thread.
- #70 (Chat UI: bubble, full-screen overlay, Clear chat) and the FAB-widening-to-every-screen it justified — gone; FAB stays Feed-only.
- #71 (admin cost/latency reporting) — gone; there's no OpenAI/Anthropic call for Expenso to meter, since the Member's own ChatGPT/Claude subscription pays for the call, not Expenso's API key.
- The chat half of #73 ("your usage this month") — gone for the same reason; the Receipt half is unaffected.
- Any chat-specific logging or rate limiting — deliberately not added. The 4 read methods already have no rate limiting and a connector caller carries the same Family-scoped permission boundary as any other caller, so this isn't a new abuse class. Zero conversation-level visibility (Expenso never sees the Member's question or the model's answer) is an accepted trade, not an oversight.

**What stays the same either way:** read-only scope (no create/update/delete tool), the 4 existing whitelisted methods as the only data surface, Family-scoped permissions as the sole access control.

**This does not make Feed/Analytics/Budget redundant.** Chat's tools call the same `get_analytics`/`get_budgets`/`get_expenses`/`get_income` the screens already use, but overlapping data sources don't make one UI a substitute for the other. Analytics in particular renders the full Category breakdown with Budget Status at a glance, no typing, every time a Member opens the app; Chat only answers whatever single question is asked, one turn at a time, and only for whoever set up a connector at all (the "power user" framing above). A future reader should not assume Chat's read access is a reason to simplify or drop any existing screen.

**Setup, if chosen:** a single admin-configured `OAuth Client` (one-time, via Desk — no self-service UI in Expenso), shared across Family members; each Member individually completes the standard OAuth login+consent flow when adding the connector on the ChatGPT/Claude side, so their token still resolves to their own Frappe user.

**Why this isn't simply better and needs a real decision, not just adoption:** it fundamentally changes where Chat lives. ADR 0004's whole premise — reachable via one thumb-tap, stacked with the FAB, matching every other screen's self-contained-PWA pattern — is traded for "reachable only if the Member already has, and opens, a separate ChatGPT/Claude app." That's a real product-surface regression for anyone without such an account, in exchange for a much smaller build (no new DocType, no new UI screen, no cost tracking to build) and zero ongoing OpenAI billing to Expenso. Revisit and decide between this and ADR 0004 before starting P5-S1 (#69) — do not build both.
