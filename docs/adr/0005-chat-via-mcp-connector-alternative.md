# Chat via MCP connector (ChatGPT/Claude) — accepted, ships before ADR 0004

**Status: accepted (2026-08-11).** #78 decided to build **both** this ADR and ADR 0004 (in-app hand-rolled tool-calling) — not one instead of the other — with this ADR's MCP connector (paired with [ADR 0006](0006-chat-driven-manual-entry-mcp-connector.md)) shipping first. Worked out in a grill-with-docs session (2026-08-06) that asked "could Chat be delivered via a ChatGPT/Claude connector instead of building #69-71?" ADR 0004's in-app design is deferred, not rejected — issues #69/#70/#71 stay open as Phase 6 and will be picked up once this ADR's MCP connector work lands; new issues track this ADR's own streaks. Motivated in part by shifting the LLM API cost off Expenso's own OpenAI billing and onto the Member's ChatGPT/Claude subscription (the same cost-shift goal ADR 0006 states explicitly) — see the "no OpenAI/Anthropic call for Expenso to meter" point below.

**Note:** a related but separate write-capable proposal — general chat-driven manual entry (`create_expense`/`create_income`, no photo required) reusing this same MCP server under a distinct write scope — is recorded in [ADR 0006](0006-chat-driven-manual-entry-mcp-connector.md), also accepted (see #79) and shipping in the same phase as this ADR.

**The alternative.** Instead of an in-app floating bubble, full-screen thread, and hand-rolled tool-calling loop inside Expenso, expose the same 4 read-only whitelisted methods (`get_expenses`, `get_analytics`, `get_income`, `get_budgets`) as tools on a remote MCP server, built with the official `mcp` Python SDK (a protocol-correctness call, not an agent-framework one — MCP's wire protocol is versioned and non-trivial to hand-roll correctly, unlike the simple bounded loop ADR 0004 rejected a framework for). Auth reuses Frappe's existing built-in OAuth2 provider (`OAuth Client` doctype, standard Authorization Code flow) — whitelisted methods already run correctly under an OAuth-resolved user via `frappe/auth.py::validate_auth()` → `validate_oauth()` → `frappe.set_user()`, so Family-scoped permissions apply with zero new permission logic. A Member reaches Chat by adding this MCP server as a connector inside ChatGPT or Claude's own app — a "power user" surface, not the bottom-bar/floating-bubble entry point issue #44 originally asked for.

**What this phase does not build yet (deferred to ADR 0004's phase, not dropped):**
- `Chat Message` DocType, `send_message`, `get_chat_history`, `clear_chat()` — not built in this phase. ChatGPT/Claude hold conversation history client-side for the MCP connector; Expenso doesn't store or see that thread. ADR 0004's own thread storage still ships later for the in-app surface.
- #70 (Chat UI: bubble, full-screen overlay, Clear chat) and the FAB-widening-to-every-screen it justified — deferred to ADR 0004's phase; FAB stays Feed-only until then.
- #71 (admin cost/latency reporting) — deferred; there's no OpenAI/Anthropic call for Expenso to meter from the MCP connector itself (the Member's own ChatGPT/Claude subscription pays for that call, not Expenso's API key), so this report has nothing to show until ADR 0004's in-app calls start producing `LLM Call Log` rows.
- The chat half of #73 ("your usage this month") — deferred for the same reason; the Receipt half is unaffected and ships now.
- Any chat-specific logging or rate limiting on the MCP connector itself — deliberately not added. The 4 read methods already have no rate limiting and a connector caller carries the same Family-scoped permission boundary as any other caller, so this isn't a new abuse class. Zero conversation-level visibility (Expenso never sees the Member's question or the model's answer) is an accepted trade, not an oversight, for this connector surface — it doesn't apply to ADR 0004's in-app thread, which does log full content.

**What stays the same either way:** read-only scope (no create/update/delete tool), the 4 existing whitelisted methods as the only data surface, Family-scoped permissions as the sole access control.

**This does not make Feed/Analytics/Budget redundant.** Chat's tools call the same `get_analytics`/`get_budgets`/`get_expenses`/`get_income` the screens already use, but overlapping data sources don't make one UI a substitute for the other. Analytics in particular renders the full Category breakdown with Budget Status at a glance, no typing, every time a Member opens the app; Chat only answers whatever single question is asked, one turn at a time, and only for whoever set up a connector at all (the "power user" framing above). A future reader should not assume Chat's read access is a reason to simplify or drop any existing screen.

**Setup:** a single admin-configured `OAuth Client` (one-time, via Desk — no self-service UI in Expenso), shared across Family members; each Member individually completes the standard OAuth login+consent flow when adding the connector on the ChatGPT/Claude side, so their token still resolves to their own Frappe user.

**Why this needed a real decision, not just adoption:** building this first changes where Chat lives for however long the in-app phase is deferred. ADR 0004's whole premise — reachable via one thumb-tap, stacked with the FAB, matching every other screen's self-contained-PWA pattern — is traded, for now, for "reachable only if the Member already has, and opens, a separate ChatGPT/Claude app." That's a real product-surface gap for anyone without such an account, accepted temporarily in exchange for a much smaller first build (no new DocType, no new UI screen, no cost tracking to build yet) and zero ongoing OpenAI billing to Expenso until ADR 0004's phase starts. Decided 2026-08-11 (#78): build both, MCP connector first.
