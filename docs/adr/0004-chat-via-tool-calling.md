# Chat via tool-calling on existing whitelisted methods, read-only, per-Member private

**Note:** an alternative — delivering Chat via an external MCP connector (ChatGPT/Claude) instead of the in-app design below — is recorded in [ADR 0005](0005-chat-via-mcp-connector-alternative.md), proposed but undecided. This ADR (0004) remains the current, committed design.

Chat (issue #44) needed a way to let the LLM answer questions about a Family's Expenses, Income, and Budgets. We chose **tool-calling against the app's existing whitelisted API methods** (`get_expenses`, `get_analytics`, `get_income`, `get_budgets`) over text-to-SQL or stuffing the Family's full transaction history into every prompt. The LLM picks which method to call and with what params (e.g. month/year); the backend executes it exactly as it does today, under the same Family-scoped permission checks every other caller goes through. This means Chat gets Family-scoping for free and never has a path to construct its own query — a hallucinated tool call fails the same way a hallucinated frontend request would, rather than opening a new class of cross-Family data leak that a generated SQL/filter approach would require re-proving safe.

The tool-calling loop itself is hand-rolled directly on the OpenAI SDK's native tool-calling — no agent framework (OpenAI Agents SDK, Pydantic AI, LangChain/LangGraph, AutoGen). With exactly 4 fixed, read-only tools and one bounded loop per message (no multi-agent handoffs, no long-running planning, no memory management beyond the last-N-messages window below), the loop is roughly "call model → execute any tool_calls → call model again → return final text" — genuinely simple enough that a framework would add dependency weight and its own abstractions without solving a problem this scope has. It also cuts against the isolation principle from ADR 0002: the OpenAI call is isolated inside one function specifically to stay simple and swappable, and wrapping a framework around it would mean isolating "LangChain," not "OpenAI" — a fuzzier boundary for no current benefit. Revisit this if the tool count or interaction complexity actually grows (write actions, multi-agent handoffs) — not preemptively.

Chat is **read-only for v1** — it can answer questions but cannot create, edit, or delete anything, matching the issue's own framing ("get info about the data stored"). This keeps the safety surface to "wrong answer," not "corrupted ledger," and avoids needing confirmation/undo flows before any write path exists.

Each Member has **exactly one continuous, ever-growing thread**, private to them — not shared with the other Member, and no concept of multiple named conversations. This is a personal-assistant framing (a Member asking a quick question) rather than the shared-ledger framing the rest of the app uses for Expenses/Income; a future reader should not assume chat inherits the Family-shared visibility pattern just because everything else in the app does.

Context sent to the LLM on each turn is the **last N messages only** (not the full thread, not a rolling summary) — bounds token cost/latency predictably as a thread ages, at the cost of losing very old context, which is an acceptable trade for a "quick question about my spending" use case. A failed response is shown as a transient notice and never persisted as a Chat Message, so thread history and the context window sent to the LLM both stay free of error noise.

Model, cost, and tracking reuse Receipt's existing infrastructure directly: `gpt-4o-mini`, the OpenAI call isolated inside its own function (mirroring `extract_receipt`'s isolation, see ADR 0002), and a row per call in `LLM Call Log` with `feature: "chat"` (see ADR 0003 — this DocType was named feature-agnostic specifically anticipating this reuse). Chat gets its own separate per-Member daily rate cap, independent of Receipt's, since it's a different usage pattern (every message is a call, sometimes more than one per message via the tool-calling loop).

**Retention.** `Chat Message` is never auto-deleted — no other DocType in this app auto-purges, and the volume is trivial for a 2-person household even over years. A Member can manually clear their own thread ("Clear chat"), which deletes all their `Chat Message` rows at once; there's no per-message delete, matching the single-ongoing-thread model.

For chat specifically (unlike Receipt), `LLM Call Log`'s `feature: "chat"` rows also capture the full tool-calling trace as content (user message, which tools were called with what params, what they returned, final answer) — Receipt's rows never needed this since the "content" there is already visible as the created Expense's fields, but chat has no equivalent artifact, and debugging a wrong answer requires seeing which tool call produced it. This is a deliberate, non-obvious asymmetry: **"Clear chat" only deletes `Chat Message` rows — it does not touch `LLM Call Log`.** A Member's cleared conversation content therefore still exists permanently in the System Manager-only admin log. This was a conscious choice (not an oversight) to keep cost/accuracy reporting complete and never lossy regardless of what Members clear; a future reader should not assume "Clear chat" is a full data-deletion guarantee.

Conversation context sent to the LLM on each turn is assembled **only from `Chat Message` rows, never from `LLM Call Log`** — this is what makes "Clear chat" actually work as a fresh start. Since `LLM Call Log` is deliberately left untouched by clearing, an implementation that built context from the log's trace data instead would silently defeat clearing entirely (old context leaking back in from a table the Member's action never reaches). `LLM Call Log` content exists solely for admin debugging, not as a context source.
