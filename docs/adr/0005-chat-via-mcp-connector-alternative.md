# Chat via MCP connector (ChatGPT/Claude) — accepted, ships before ADR 0004

**Status: accepted (2026-08-11).** #78 decided to build **both** this ADR and ADR 0004 (in-app hand-rolled tool-calling) — not one instead of the other — with this ADR's MCP connector (paired with [ADR 0006](0006-chat-driven-manual-entry-mcp-connector.md)) shipping first. Worked out in a grill-with-docs session (2026-08-06) that asked "could Chat be delivered via a ChatGPT/Claude connector instead of building #69-71?" ADR 0004's in-app design is deferred, not rejected — issues #69/#70/#71 stay open as Phase 6 and will be picked up once this ADR's MCP connector work lands; new issues track this ADR's own streaks. Motivated in part by shifting the LLM API cost off Expenso's own OpenAI billing and onto the Member's ChatGPT/Claude subscription (the same cost-shift goal ADR 0006 states explicitly) — see the "no OpenAI/Anthropic call for Expenso to meter" point below.

**Note:** a related but separate write-capable proposal — general chat-driven manual entry (`create_expense`/`create_income`, no photo required) reusing this same MCP server under a distinct write scope — is recorded in [ADR 0006](0006-chat-driven-manual-entry-mcp-connector.md), also accepted (see #79) and shipping in the same phase as this ADR.

**The alternative.** Instead of an in-app floating bubble, full-screen thread, and hand-rolled tool-calling loop inside Expenso, expose the same 4 read-only whitelisted methods (`get_expenses`, `get_analytics`, `get_income`, `get_budgets`) as tools on a remote MCP server, built with `frappe-mcp` (the official `frappe`-org WSGI-native MCP library — see the implementation note below for why this replaced an earlier plan to use the official async `mcp` Python SDK directly) — a protocol-correctness call, not an agent-framework one, matching the same reasoning ADR 0004 used to reject a framework for its own tool-calling loop: MCP's wire protocol is versioned and non-trivial to hand-roll correctly, but the loop logic itself doesn't need one. Auth reuses Frappe's existing built-in OAuth2 provider (`OAuth Client` doctype, standard Authorization Code flow) — whitelisted methods already run correctly under an OAuth-resolved user via `frappe/auth.py::validate_auth()` → `validate_oauth()` → `frappe.set_user()`, so Family-scoped permissions apply with zero new permission logic. A Member reaches Chat by adding this MCP server as a connector inside ChatGPT or Claude's own app — a "power user" surface, not the bottom-bar/floating-bubble entry point issue #44 originally asked for.

**What this phase does not build yet (deferred to ADR 0004's phase, not dropped):**
- `Chat Message` DocType, `send_message`, `get_chat_history`, `clear_chat()` — not built in this phase. ChatGPT/Claude hold conversation history client-side for the MCP connector; Expenso doesn't store or see that thread. ADR 0004's own thread storage still ships later for the in-app surface.
- #70 (Chat UI: bubble, full-screen overlay, Clear chat) and the FAB-widening-to-every-screen it justified — deferred to ADR 0004's phase; FAB stays Feed-only until then.
- #71 (admin cost/latency reporting) — deferred; there's no OpenAI/Anthropic call for Expenso to meter from the MCP connector itself (the Member's own ChatGPT/Claude subscription pays for that call, not Expenso's API key), so this report has nothing to show until ADR 0004's in-app calls start producing `LLM Call Log` rows.
- The chat half of #73 ("your usage this month") — deferred for the same reason; the Receipt half is unaffected and ships now.
- Any chat-specific logging or rate limiting on the MCP connector itself — deliberately not added. The 4 read methods already have no rate limiting and a connector caller carries the same Family-scoped permission boundary as any other caller, so this isn't a new abuse class. Zero conversation-level visibility (Expenso never sees the Member's question or the model's answer) is an accepted trade, not an oversight, for this connector surface — it doesn't apply to ADR 0004's in-app thread, which does log full content.

**What stays the same either way:** read-only scope (no create/update/delete tool), the 4 existing whitelisted methods as the only data surface, Family-scoped permissions as the sole access control.

**This does not make Feed/Analytics/Budget redundant.** Chat's tools call the same `get_analytics`/`get_budgets`/`get_expenses`/`get_income` the screens already use, but overlapping data sources don't make one UI a substitute for the other. Analytics in particular renders the full Category breakdown with Budget Status at a glance, no typing, every time a Member opens the app; Chat only answers whatever single question is asked, one turn at a time, and only for whoever set up a connector at all (the "power user" framing above). A future reader should not assume Chat's read access is a reason to simplify or drop any existing screen.

**Setup:** a single admin-configured `OAuth Client` (one-time, via Desk — no self-service UI in Expenso), shared across Family members; each Member individually completes the standard OAuth login+consent flow when adding the connector on the ChatGPT/Claude side, so their token still resolves to their own Frappe user.

**Implementation note: MCP server library, Frappe v16, and auth-spec compliance (researched 2026-08-11, ahead of #80).**

- **Correction to an earlier version of this note:** a first pass concluded "Frappe v16 changes nothing for OAuth2," based on `gh api compare version-15...develop` returning zero OAuth-related files. That was a false negative — GitHub's compare API silently truncates the file list on a branch diff this large (~18 months of unreleased work), it wasn't evidence of no changes. Reading `frappe/integrations/oauth2.py` directly off `develop` shows substantial, real changes. Recorded here so a future reader trusts the corrected conclusion below, not the discarded one.
- **Use `frappe-mcp` (pip `frappe-mcp`, official `frappe`-org repo), not the official async `mcp` Python SDK directly.** The official SDK requires ASGI; Frappe is WSGI — `frappe-mcp` exists specifically to bridge that gap. The MCP server runs as a normal Frappe whitelisted method (`@mcp.register()` on a function, served at `/api/method/<app>.mcp.handle_mcp`), in-process, no separate ASGI/uvicorn sidecar needed (superseding an earlier draft of this note, which proposed exactly that sidecar). Tradeoff: `frappe-mcp`'s own README calls it "highly experimental... bugs, breaking changes... mostly without notice." Accepted as a contained, reversible bet for #80 — if it proves too unstable mid-build, the fallback is the official SDK plus a small separate ASGI process, which remains a documented, understood alternative, not something to research from scratch if needed.
- **Requires upgrading the bench to Frappe v16.** Decided 2026-08-11: worth it. PR frappe#33188 (merged into `develop` 2025-07-04) adds exactly what the MCP auth spec (2025-11-25) requires and v15.92 (the installed version) lacks: RFC 8414 Authorization Server Metadata at `/.well-known/oauth-authorization-server` — including `code_challenge_methods_supported: ["S256"]`, the field whose absence would make a spec-compliant client refuse to connect at all — RFC 9728 Protected Resource Metadata at `/.well-known/oauth-protected-resource`, RFC 7591 Dynamic Client Registration at `.../register_client`, and CORS handling for public clients. All gated behind a new `OAuth Settings` doctype's checkboxes (`show_auth_server_metadata`, `show_protected_resource_metadata`, `enable_dynamic_client_registration`) — enable the first two for #80; DCR isn't needed since this ADR already uses pre-registration (a single admin `OAuth Client`), which the MCP spec treats as the first-priority client-registration mechanism anyway. `frappe-mcp`'s own auth docs assume these v16 endpoints exist — without them, `frappe-mcp` still works but degrades to the same manual-pre-registration-only path v15.92 would require, missing the discovery metadata a spec-compliant client expects.
- **What Frappe already got right even on v15, confirmed by reading the source, and unchanged by the v16 upgrade:** full Authorization Code flow; PKCE with both `S256` and `plain` (`frappe/oauth.py:90-179`); token revocation and introspection; scopes via `OAuth Scope`/`OAuth Client Role` (fits `expenso:read`/`expenso:write` from ADR 0006 natively). v16 adds the missing discovery/metadata layer around this, not a replacement for it.
- **A gap accepted, not built, on either version:** RFC 8707 resource indicators (binding a token to one specific `resource` URI) aren't implemented in Frappe's oauthlib-based flow, v15 or v16. For a multi-tenant authorization server serving many different resource servers this is a real security requirement; for Expenso — one Frappe site issuing tokens only ever usable against that same site's own MCP endpoint — there's no other resource a stolen token could be replayed against. Documented here as an accepted deviation, not an oversight.
- **Framework choice reconsidered and confirmed, not just assumed.** The auth-spec friction above prompted an explicit "should Expenso move off Frappe" check — rejected. MCP's ecosystem-wide immaturity (the spec itself is roughly a year old and still revising its own auth model — three spec-generation differences surfaced just in this research pass) makes this kind of DIY bridging normal everywhere right now, not a Frappe-specific weakness; Frappe's first-party investment here (`frappe-mcp`, PR #33188) is ahead of most comparably-sized frameworks, not behind. Rewriting Phases 1-4's DocTypes, permissions, PWA, and realtime layer to smooth out one still-optional, already-deferred-behind-Phase-6 connector feature was judged not worth it. Decided 2026-08-11: stay on Frappe, upgrade to v16.

**Why this needed a real decision, not just adoption:** building this first changes where Chat lives for however long the in-app phase is deferred. ADR 0004's whole premise — reachable via one thumb-tap, stacked with the FAB, matching every other screen's self-contained-PWA pattern — is traded, for now, for "reachable only if the Member already has, and opens, a separate ChatGPT/Claude app." That's a real product-surface gap for anyone without such an account, accepted temporarily in exchange for a much smaller first build (no new DocType, no new UI screen, no cost tracking to build yet) and zero ongoing OpenAI billing to Expenso until ADR 0004's phase starts. Decided 2026-08-11 (#78): build both, MCP connector first.
