# Chat feature: provider-agnostic backend via LiteLLM, tool-use grounding, read-only, no persisted history

Expenso's new Chat tab lets a Member ask questions about their Family's stored data. Rather than pinning to one LLM vendor, the backend calls providers through **LiteLLM**, a thin Python library that normalizes chat + tool-calling across OpenAI, Anthropic, and other providers behind one `completion(model=, messages=, tools=, api_key=)` call — switching providers is a config change, not a code change. We considered LangChain but rejected it: its agent/chain abstractions are built for multi-step orchestration we don't need, since the tool-call loop itself (capped at 5 iterations, see below) stays hand-written either way; LiteLLM adds far less dependency weight for the same provider-agnostic outcome.

Provider and credentials live in a new Single DocType, **Expenso Desk Settings** — a `Model` field (free text, LiteLLM's `<provider>/<model>` string format, e.g. `openai/gpt-4o-mini` or `anthropic/claude-sonnet-5-20250929`) and an `API Key` field (Frappe's `Password` fieldtype, encrypted at rest). It's named distinctly from the Member-facing "Settings" screen to avoid colliding with that existing glossary term — this DocType is Desk-only, editable only by a System Manager, never exposed in the SPA. One key is shared by every Family on the instance (matching the existing single-site, multi-Family model — the instance owner runs one Frappe site and pays for one LLM account, the same way there's one Frappe site for all Families). No `api_base` field in v1 — can be added later as a third optional field without disrupting the other two.

The LLM answers by calling existing family-scoped whitelisted functions in `api.py` (`get_expenses`, `get_analytics`, `get_budgets`, ...) as tools, in-process rather than a second HTTP round trip, rather than stuffing a month's data into every prompt. Chat is read-only — it cannot create, edit, or delete records — and it declines questions it can't ground in the Family's own data. Each message is a single blocking whitelisted method call: the backend runs the full tool-call loop server-side (capped at 5 calls before forcing a final answer, guarding against a runaway loop against the shared key) and returns the finished answer in one response — no streaming transport, matching the rest of the app's plain-REST pattern rather than adding SSE/WebSocket plumbing on top of Feed's existing (and unrelated) realtime-refresh WebSocket use. There is no per-day message limit for this first version. Conversation history is not persisted: it lives only in the frontend's Pinia store for the duration of the visit and resets on refresh, matching the app's existing ephemeral UI-state pattern (`month.js`).

## Considered Options

- LangChain instead of LiteLLM — rejected for dependency weight and unneeded agent/chain abstractions; LiteLLM's single-function surface is enough since the loop itself is hand-written regardless.
- OpenAI-only backend (original draft of this ADR) — superseded; provider lock-in wasn't a real requirement and LiteLLM removes it at low cost.
- Per-Family API key instead of one global key — rejected for v1: more setup friction per Family and a bigger permissions surface, with no clear need yet since there's one instance owner today.
- Streaming responses — rejected for v1 to avoid a new transport; can be revisited if multi-tool-call answers feel slow in practice.
- Persisting conversation history in a new `Chat Message` DocType — rejected to keep the first streak's scope small and avoid a new permission surface; can be revisited if Members want history across sessions.
