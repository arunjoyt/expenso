# General chat-driven manual entry via MCP connector — accepted

**Status: accepted (2026-08-11, #79).** Recorded in the same grill-with-docs session as [ADR 0005](0005-chat-via-mcp-connector-alternative.md) (2026-08-06), motivated by the same cost-shift goal (LLM cost on the Member's own ChatGPT/Claude subscription, not Expenso's OpenAI billing) plus removing app-switching friction for quick manual entries. A receipt-photo-scoped version of this idea was considered first and abandoned: requiring an image kept the risk surface tightly bound to Receipt (a photo to cross-check against, a clear vision-extraction cost story), but the actual goal was broader — friction-free entry generally, with or without a photo — so this ADR documents that broader, riskier scope directly rather than as a Receipt side effect. Ships in the same phase as ADR 0005, before ADR 0004's in-app Chat (deferred, not dropped — see #78). #66/#67/#68 (Receipt) are unaffected and remain the plan of record for the in-app, reviewed path.

**The proposal.** Two new write-capable MCP tools, `create_expense` and `create_income`, added to the same MCP server as Chat's read-only tools (ADR 0005), gated by a separate OAuth scope (`expenso:write`, distinct from Chat's `expenso:read`) so a Family can grant read-only Chat access without also granting this. A Member types something like "add a $50 dinner expense" directly in ChatGPT/Claude; the calling LLM parses it and calls the appropriate tool with the extracted fields — no image, no in-app step, no review.

**Scope, resolved in this session:**
- **Expense and Income, create-only.** No edit or delete via chat — identifying *which* existing record a conversational reference like "that coffee expense" means is an unsolved disambiguation problem, and a wrong match would silently corrupt or delete the wrong record. Symmetric with Expense (both are simple, no-approval, single-record writes in-app today), so there's no principled reason to support one and not the other once generalizing beyond receipts.
- **Immediate write, no review step.** Same tension as Chat/Receipt: a confirm-in-app step would reintroduce the exact friction this proposal exists to remove. Accepted as the defining trade-off, not something to design around.
- **Original message text stored verbatim** on the created record (passed through from the calling LLM, not re-derived) — the after-the-fact safety net once in-flow review is gone, since there's no receipt photo to fall back on for text-only entries. Shown in the record's detail view (not the Feed list, to avoid clutter), not the Feed row itself.
- **Visible marker** on any record created this way, distinguishing it from anything a Member entered or reviewed in-app (including Receipt's in-app capture flow, which does have review). One marker covers this and any future revival of the receipt-only variant — both share the same "unreviewed external write" risk.
- **One combined per-Member daily write cap** across both tools — bounds total unreviewed-write volume per day regardless of which tool or how the calls are split; a per-tool cap would leave an alternating-tool loop unbounded.
- **`amount` is the only hard-required field; `date` defaults to today if not stated.** A receipt almost always has a printed date; a typed message usually doesn't. Requiring an explicit date would reject most real messages and defeat the point. This mirrors the existing in-app default (Income already defaults `date` to today).
- **Category/Source must match an existing record** (via companion `list_categories`/`list_sources` read tools) — unmatched values are rejected/nulled, never auto-created. An unreviewed write already accepted for the record itself shouldn't also be allowed to silently expand the Family's Category/Source lists, which have their own deliberate management flow (Settings, or intentional inline-create in the manual Add Expense/Income sheet).
- **No `LLM Call Log` rows for this path** — Expenso makes no OpenAI call (the calling LLM does its own parsing on the Member's subscription), so there's nothing to meter, consistent with Chat's connector (ADR 0005).
- **Same MCP server as Chat**, scope-gated rather than a separate server — one `OAuth Client` registration, one connector URL, scope separation (above) does the actual access-control work.

**Update (2026-08-23, after #81 shipped and was verified live via a real Claude connector against a receipt-derived batch of Expenses): added a separate `notes` parameter, and stopped displaying `message`/`external_write_message` anywhere in the app.** Real usage surfaced a gap this ADR hadn't anticipated: a calling LLM parsing a receipt (or a typed message) naturally produces a short human-readable label per line item (e.g. "Nahkauf - Küchentücher") — exactly what `notes` is for on a manually-entered record — but `create_expense`/`create_income` had no `notes` parameter, so that label had nowhere to go except the audit-trail `message` field, which the detail view then quoted verbatim next to the marker. That made chat-created records look and read differently from manual ones for no good reason, and pushed the actually-useful summary one tap deeper than a normal entry's Notes. Fix: `notes` is now a first-class parameter, stored on the record's own `notes` field and shown everywhere a manual entry's Notes already show (Feed row included) — no Feed-clutter concern here since this is the same field/display every entry already uses. `message` still exists and is still stored on `external_write_message` (the original "after-the-fact safety net" reasoning above still holds — the raw request text is worth keeping for accountability), but the app no longer renders it anywhere; the detail-view marker is now a static "💬 Unreviewed external write" label with no quoted text under it. The marker itself, the daily cap, the create-only scope, and the Category/Source matching rules are all unchanged.

**Resolved risk:** the write-safety trade-off (immediate, unreviewed writes to the Family's real ledger, bounded only by a marker, a stored message, and a daily cap) was explicitly accepted over Receipt's in-app review step, as part of the 2026-08-11 decision (#79) — friction-free entry with no review step is the point, not a residual risk to design around further.

**Combined effect with ADR 0005.** This ADR's write tools and 0005's read tools share one MCP server (Q8), so adopting both together consolidates Chat and Receipt's external surface into a single interface: one connector, one conversation in ChatGPT/Claude, covering both "ask a question" and "add a record" (typed or photo-derived — the tool doesn't distinguish how the calling LLM arrived at the fields). This does not affect the in-app paths: manual Add Expense/Add Income and Receipt's in-app camera capture (#66/#67, ADR 0002/0003) stay as the reviewed alternative regardless of the connector, and ADR 0004's in-app Chat UI (#70) still ships later as an additional surface, not a redundant one — once both exist, #70 gives an entry point that doesn't require a separate ChatGPT/Claude app.
